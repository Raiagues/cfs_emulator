# Flight Studio: implementation brief (read this first)

You are implementing changes in the Flight Studio repository (`github.com/Raiagues/cfs_emulator`, branch `first-flight-flow`). This folder (`docs/design-pack/`) is the single source of truth for what to build. Read every file in the order below before you change any code. Do not skim. When this pack and the existing code disagree, the pack wins, unless the pack says to keep the existing behaviour.

Flight Studio is a lab for learning and developing NASA cFS flight software. It runs cFS natively on Linux, inside a QEMU Raspberry Pi 4B emulator, or on a real Raspberry Pi. It is never for flight. Everything a user learns here must transfer directly to the real NASA cFS workflow: the official repository, the official app names (ci_lab, to_lab, sch_lab, sample_app), cFE services (ES, EVS, SB, TBL, TIME, FS), OSAL and PSP. After using Flight Studio, a person must be able to do the same things on their own computer from the terminal.

## How to work

1. **Plan before coding.** Write `docs/design-pack/WORKPLAN.md`: for each screen and each infrastructure item, list the files you will touch, what you will delete, and which acceptance tests cover it. Keep it updated as you go.
2. **Map before changing navigation.** Generate `docs/design-pack/NAVIGATION_MAP.md` from the code: every button, link, tab, step and keyboard shortcut, its handler, the route or state it changes, the endpoint it calls and the server handler. Compare it with the map in `03_FIRST_RUN_FLOW.md`. Fix every mismatch. The final map must match `03` exactly and must be generated by a script (`scripts/nav-map`), not by hand, so it can be re-run in CI.
3. **Separate infrastructure from the UI** as described in `02_ARCHITECTURE.md`. Every action the UI performs must exist first as a CLI command that works with no browser. The UI calls the same code through the HTTP API.
4. **Build the screens from the design pack**, one screen at a time, in the order of `03_FIRST_RUN_FLOW.md`. After each screen, run its acceptance tests and take screenshots at 1440×900 in dark and light themes; compare them with `design/screens/`.
5. **Delete, don't patch.** Remove dead code, duplicated helpers, unused CSS and workarounds listed in `10_AUDIT_FINDINGS.md`. Never add a timeout, retry, sleep or flag to hide a race or an ordering bug; fix the cause.
6. **Rewrite the README** following `07_README_SPEC.md`, and verify every command in it on a clean checkout.
7. **Run the full acceptance suite** in `09_ACCEPTANCE_TESTS.md` and paste the results into `docs/design-pack/RESULTS.md`.

## Hard rules

- Do not invent product features, screens, texts or options that are not in this pack. If something is missing, write it in `docs/design-pack/QUESTIONS.md` and keep going with the rest.
- Do not pre-fill or pre-complete anything the user should do themselves during the first run. The user sends the first command, creates the first app and writes the first line. Values a real operator would type (such as the ground IP 127.0.0.1) appear as placeholders, never as pre-filled values; nothing is preselected on the first visit (not even the Native target).
- Exactly one next action is highlighted at any moment of the guided flow, using the single coach style in `05_ANIMATION_SPEC.md`. Never two competing highlights, never none while the user is expected to act.
- Every animation listed in `05_ANIMATION_SPEC.md` is required. An animation that is missing, replaced by a static state, or shortened is a failed requirement. Tests in `09` check this; do not disable them.
- No hacks: no hard-coded paths of the author's machine, no `sleep` to wait for processes, no swallowed exceptions, no `TODO` left in shipped code, no feature flags to hide unfinished work, no copying of NASA code into the repo when it can be fetched.
- Do not break what already works. The current build, run, ground link, CSRF/token protection, host checks, path traversal checks and sensor models stay working. Run the existing tests before and after each change.
- One page per screen, no page scroll at 1440×900, no horizontal scroll at 1280×720.
- Text in the interface is short, human and operational. No banners, no warnings that repeat what the screen already shows, no marketing words. See the wording rules in `01`.

## Definition of done

- `09_ACCEPTANCE_TESTS.md` passes completely on a fresh clone, on Linux, with the commands in the new README.
- `NAVIGATION_MAP.md` (generated) equals the map in `03_FIRST_RUN_FLOW.md`; no control leads somewhere other than its label says.
- Screenshots of every screen in `RESULTS.md`, next to the matching reference in `design/screens/`.
- `10_AUDIT_FINDINGS.md` items marked "must fix" are fixed, each with the commit that fixed it.
